AMLOK Sandbox includes six fictional businesses and 32 executable scenarios. The businesses supply recognizable test identities and source information. Scenarios control the condition you want to test and the illustrative policy used for that run.

## The six businesses

| Business | Market | Industry | Starter scenario | What to inspect |
| --- | --- | --- | --- | --- |
| Maple & Pine Retail Ltd. | CA | Retail | `healthy` | A completed underwriting with a within-policy recommendation. |
| Harbor Route Logistics Inc. | US | Transportation | `outside_policy` | A completed underwriting with an outside-policy recommendation. |
| Cedar Cloud Software Inc. | CA | Software | `manual_review` | A review-required result caused by unavailable policy inputs. |
| Prairie Precision Manufacturing Ltd. | CA | Manufacturing | `document_required` | An Origination waiting for an additional document. |
| Summit Table Hospitality LLC | US | Hospitality | `source_reauthorization` | An Origination requiring renewed source authorization. |
| Atlas Supply Wholesale Ltd. | CA | Wholesale | `provider_failure` | A failed processing result and its failure details. |

Each business includes synthetic bank, accounting, payments, commerce and verification information; normalized source records and provenance; six downloadable PDF reports and documents; consent and connections; lending-product and policy versions; and an Origination. Completed assessments include results, evidence, exports and funded monitoring. Cases that need action retain the requirement or error to help you build recovery flows.

The sample history covers twelve complete calendar months, with categorized transactions and daily closing balances. Canadian business figures use CAD and US business figures use USD; workspace billing examples remain CAD. See [sample data and documents](/sandbox/sample-package) for the full contents, financial relationships and working document-download example. These fixtures are illustrative, not a production-volume dataset.

## Run and inspect a scenario

1. Open **Dev Tools > Sandbox scenarios**.
2. Select the scenario category, scenario and fictional business.
3. Review **Expected result** before you run it.
4. Choose **Run scenario**, or execute the provided request from your backend.
5. Open **Run history** to inspect requests, responses, assertions and generated resource IDs.
6. Retrieve those records through their normal API endpoints or open them in the console.

The same business can produce different outcomes when you choose different scenarios. For example, `healthy` uses a passing test policy, while `outside_policy` uses a failing threshold. These are test assessments, not decisions about actual businesses.

<Info>
**Scenario completion and business outcomes are different.** A scenario can complete successfully because it correctly produced a failed underwriting, a declined payment or a missing-document requirement. A failed scenario means a step or expected check did not finish as intended.
</Info>

## Test monitoring events and webhook delivery

Sample preparation records events without sending webhooks. Read them under **Dev Tools > Deliveries & events** or through `GET /v1/events`. An event marked **Recorded** is not proof that an HTTP request reached your application.

To exercise your receiver, configure an enabled Sandbox endpoint, select it for a run and explicitly enable delivery. Webhook scenarios require the appropriate event scopes and subscriptions. Sandbox delivery sends real HTTP requests to that test endpoint, even though the payloads are fictional. Keep the receiver separate from production actions.

Inspect delivery history and your receiver's logs to verify arrival and attempts. Duplicate delivery retains the event ID; retries and concurrent delivery can change arrival order. You can return `503` and then `2xx` from your receiver to exercise the retry path. See [webhook testing details](/api-reference/sandbox-journeys#webhooks-and-monitoring).

Monitoring scenarios let you create a deterioration event, restore the fixture and resolve the prior alert. **Evaluate monitoring now** evaluates a run-owned active monitor. It does not advance server time or change billing periods.

## Repeat without losing your history

**Repeat with fresh records** creates a new run and new linked records. It preserves previous results, logs and immutable ledger entries. Keep run IDs in your tests, and use new idempotency keys for new executions. Reuse a key only to retry the same intended command.

For request bodies, permissions and automated execution, use the [API scenario guide](/api-reference/sandbox-journeys), [runnable client](https://raw.githubusercontent.com/amloktech/docs/main/downloads/run-sandbox-scenario.mjs) and **Data Lookup** in the console.

## Inspect financial evidence and missing inputs

The sample package includes six fictional businesses with different financial profiles. Scenario traces request `view=summary` for risk packages so the complete six-business journey stays readable. Retrieve the linked package directly, follow its paged section views or use its export request for full detail. The trace preserves the actual request and response; it does not truncate a full package. Run a scenario, retrieve its risk package, and follow a metric's `inputs[].evidence[]` to the frozen record and `field_path`. Banking examples include explicit coverage, transaction classifications and daily balances; accounting examples include a typed supporting schedule. Document records retain controlled download links.

Compare operating receipts with debt proceeds and owner contributions. Inspect cash-buffer days, receivable/payable/inventory days, receipt timing and observed cash-shock episodes. Read the metric's window, currency, version and missing reason before using its value. A review or missing-input scenario can legitimately return unavailable metrics.

Use **Dev Tools → Data Lookup** to inspect the request, response and field definitions. Discover scalar policy keys through `GET /v1/configuration`; use the returned calculation version when creating a risk-policy version. A required unavailable metric produces review instead of passing silently.

Existing saved results keep their original catalog. New runs use the current definitions, while missing source coverage remains explicit. Loading or resetting sample data is an explicit workspace action; a catalog update does not erase your existing Sandbox records. See [risk-package methodology](/api-reference/risk-package-methodology) for formulas and observation requirements. All sample businesses, funds and conclusions are synthetic.
