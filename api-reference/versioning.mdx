AMLOK publishes one `/v1` API. The OpenAPI info.version and response meta.schema_version identify the contract revision. There is no separate legacy reference. The current 1.0.0 document is the implementation specification before backend release.

Before the first backend release, align code, fixtures, guides, generated client artifacts and console Data Lookup to the same contract hash. A deployed environment must expose that revision in responses and pass the acceptance checklist.

## After release

Within a released major API, adding an optional response field or a new independent operation is additive. Clients must ignore unknown response fields, preserve opaque IDs/cursors and tolerate additional event types by safely recording or ignoring unknown events without crashing. Requests remain strict: reject unsupported input fields with 422 rather than silently discarding them.

Removing/renaming fields or operations, adding required request fields, changing units/semantics, changing nullability to invalidate accepted values, or adding states to a closed status enum are breaking changes. They require an explicit contract review and a published adoption plan before deployment. Do not silently change a released contract or introduce an undocumented alternative API.

Record changes in the [contract change log](/api-reference/contract-changelog), notify institution technical contacts before an affected release and test generated consumers. Security revocation and entitlement changes still take effect when required; they do not authorize changing historical evidence or billing entries.

Published packages and financial records preserve their original schema/calculation/rate versions. A new metric calculation version affects new results only. Provider-specific coverage changes must remain visible as data availability information.
