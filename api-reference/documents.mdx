Upload documents with `POST /v1/documents` using multipart form data. Documents can support a borrower, a lending-product version or a risk-policy version. Every upload creates a new immutable record.

```bash
curl --request POST --fail-with-body --max-time 30 \
  "${AMLOK_API_BASE_URL}/v1/documents" \
  --header "Authorization: Bearer ${AMLOK_API_KEY}" \
  --header 'Accept: application/json' \
  --header 'Idempotency-Key: uploadDocument-synthetic-0042' \
  --form file=@/path/to/financial-statement.pdf \
  --form context=borrower \
  --form borrower_id=bor_synthetic \
  --form document_type=financial_statement
```

Use `context: borrower` with `borrower_id`; add `origination_id` and `requirement_id` when satisfying an existing requirement. For `lending_product` or `risk_policy`, omit borrower/origination/requirement fields and reference the returned document ID in the new configuration version.

An upload returns `202` while inspection and processing occur. Retrieve its metadata until available or rejected. The filename, MIME type, byte length and SHA-256 describe the retained file. Metadata access does not imply download permission.

Create a short-lived link with `POST /v1/documents/{id}/download-links`, supplying an authorized purpose. The server checks workspace, environment, borrower authorization, consent and provider entitlement again. Do not log signed links, send them in webhooks or treat an expired link as a missing document. Request a new link when permitted.

Use the original files and provider reports referenced by [evidence](/api-reference/evidence-traceability). There is no update or delete operation for product documents.

## Discover and associate files

[GET /v1/documents](/api-reference/endpoints/evidence/list-documents) lists files by `borrower_id`, `origination_id`, `context`, `document_type` and `status`. `origin` distinguishes `institution_upload`, `borrower_upload`, `integration` and `amlok_generated`. Follow `next_cursor` until `has_more` is false and preserve the same filters across pages.

| Your goal | Query or reference |
| --- | --- |
| Find all files for one identity, including later uploads | `GET /v1/documents?borrower_id=...` |
| Find an origination's primary and participant files, plus uploads targeted at it | `GET /v1/documents?origination_id=...` |
| Identify the exact evidence published with a completed result | The risk package's frozen `document_ids`, `participants[].document_ids` and evidence references |

The origination filter resolves associations from the origination, not just each document's upload metadata. `Document.origination_id` can remain `null` when an initially uploaded file is later included in one or more assessments. Other filters narrow the same result: adding `borrower_id` excludes files owned by different participants. A missing or foreign-workspace/environment origination returns `404`.

Association membership is fixed at the listing snapshot. Start a new listing to see later accepted associations. Current source authorization is checked again, so access can become restricted even when a page belongs to an earlier snapshot. An associated upload can still be processing or rejected; listing it does not establish that underwriting used it.

## Submit initial documents

1. Upload each file with `context=borrower` and the correct `borrower_id`. Save the returned document ID.
2. Read `GET /v1/documents/{id}` until `status` becomes `available` or `rejected`. `202` is an upload receipt, not a readiness confirmation. Inspect `failure` if rejected and upload a corrected file with a new command key.
3. Include available primary-borrower IDs in `CreateOrigination.document_ids`. Put a related party's files in that participant's `document_ids`.
4. Submit the origination. The server checks ownership, context and availability; processing or rejected files return `422` instead of creating a waiting origination.

Uploading a file for a borrower after creating an origination does not attach it to that origination. In the Console, **Documents → Other borrower documents** makes those files discoverable without presenting them as evidence for the existing assessment.

## Resolve an open requirement

For an open document requirement, upload a new file with `borrower_id`, `origination_id` and `requirement_id`. Use the borrower named by the requirement, including a related party when applicable. The server checks context, document type and accepted MIME type. The receipt records the target immediately, so the file appears in the origination document listing while processing. Only successful inspection accepts the file into the primary or participant document IDs and resolves the requirement while the origination remains open. `requirement_id` cannot be supplied without `origination_id`. Later association is permitted only while the origination is `collecting` or `requires_action`; other states return `409`. Completed assessments and files are never overwritten.

## Include a later file in a new assessment

The origination retains its immutable `submitted_request` and accepted document associations. The completed risk package freezes `document_ids` and its evidence set. A later upload alone does not change either the result or its published evidence. Wait for the new file to become available and include it explicitly in the next request. For changed application information, finish or cancel the existing attempt, then create a new Origination using the same application reference, `supersedes_origination_id` and a new command key; do not modify the historical application. A document status notification identifies the file to retrieve without including file contents or a signed URL.

## Validation and rejection

Read allowed_document_mime_types, document_types, max_upload_bytes and max_document_pages from configuration.operational_profile. [Operating limits](/api-reference/operating-profile) defines 413/415 behavior, asynchronous rejection, encrypted-file handling and integrity checks. Rejected documents expose structured failure; available documents have failure null. Every document exposes record_version for event reconciliation.

## Identity, participants and archived intake

Upload initial borrower documents before submitting the assessment and associate returned IDs with the correct identity. Related-party files use that participant's own `borrower_id` and appear in its typed `participants[].document_ids`. The primary borrower's document list cannot borrow another person's files. Participant files must be available when submitted.

An archived borrower rejects new uploads. Restoration permits new intake but does not alter previous files or assessment evidence. Archival is not file deletion; no automatic purge period is implied. Follow your agreement and support process for retained-data requests.
