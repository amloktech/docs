Signal refreshes authorized sources and reassesses funded deals against the institution's policy. You enroll the deal; AMLOK manages collection, normalization, baseline preparation and included calculations.

## Enroll a funded deal

```bash
curl --request POST --fail-with-body --max-time 30 \
  "${AMLOK_API_BASE_URL}/v1/monitors" \
  --header "Authorization: Bearer ${AMLOK_API_KEY}" \
  --header 'Accept: application/json' \
  --header 'Idempotency-Key: createMonitor-synthetic-0042' \
  --header 'Content-Type: application/json' \
  --data '{"borrower_id":"bor_synthetic","deal":{"institution_reference":"LOAN-0042","funded_amount":{"amount":"50000.00","currency":"CAD"},"outstanding_amount":{"amount":"50000.00","currency":"CAD"},"funded_at":"2026-11-05T12:00:00Z","maturity_date":"2027-11-06","repayment_frequency":"monthly","terms_document_ids":[]},"baseline":{"risk_package_id":"rp_synthetic"},"risk_policy_version_id":"rpv_synthetic","cadence_id":"cadence_synthetic","connection_ids":["con_synthetic"]}'
```

The baseline is either an existing risk-package ID or typed baseline.portfolio inputs with lending_product_version_id, nullable application and document_ids. Do not send both. Portfolio onboarding does not require purchasing a new Insights assessment. The server validates that the baseline, borrower, policy and connections belong to the same authorized context.

`202 Accepted` means enrollment is initializing. Retrieve the monitor to observe activation, action requirements or funding requirements. Cadences come from configuration; provider webhook support does not establish a universal refresh frequency or SLA.

## Inspect each evaluation

`GET /v1/monitoring-runs?monitor_id=...` returns the evaluation history. Each run exposes per-integration source freshness, coverage, limitations, its evidence set and the resulting risk-package ID. Drill into evidence for normalized records and authorized provider reports or original files.

A partial, failed or skipped sync does not mean the borrower passed a risk check. Read source coverage and package limitations before interpreting an alert or comparison. A Signal package links the previous package for traceable changes.

## Alerts, events and deliveries

- **Alert:** the system-derived risk condition with rule, severity, previous/current values and evidence.
- **Event:** a durable notification that an alert, run or other resource changed.
- **Delivery:** an HTTP attempt to send the event to your configured destination.

Read alerts through `GET /v1/alerts?monitor_id=...`, receive signed events and troubleshoot delivery attempts separately. Replaying a delivery does not rerun monitoring. Your institution performs outreach, collections and case management in its own systems.

## Change future configuration

Use `PATCH /v1/monitors/{id}` with the ETag returned by the monitor. You may change its future policy, cadence or active/paused/stopped state. A stale ETag returns `412`. A replacement risk policy must retain the existing policy's borrower type and market; an incompatible policy returns `422 validation_error` and leaves the monitor unchanged. A stopped Monitor can be explicitly reactivated with `status: active` after current prerequisites pass; reuse its ID and facility reference. Neither a configuration change nor an alert resolution rewrites historical packages, evidence or charges.

Signal includes change-driven reassessment. A separately requested full underwriting is Insights. Signal counts a borrower/business once per workspace/month, using its combined workload; see [consumption reporting](/api-reference/consumption-reporting).


Current lender balance and terms arrive through [immutable deal snapshots](/api-reference/deal-inputs). Read [processing states and recovery](/api-reference/processing-lifecycle) for typed requirements, consent renewal and funding resumption.

## Start without a previous underwriting

A Signal-only integration registers or reuses the borrower, obtains `continuous_monitoring` consent, uploads the funded facility's documents, and creates the required product and policy versions. Submit `POST /v1/monitors` with `baseline.portfolio`, containing `lending_product_version_id`, `application` (the supplied application or null when unavailable), and `document_ids`. Supply the funded `deal`, `risk_policy_version_id`, `cadence_id` and authorized `connection_ids` as usual.

This path creates monitoring and its baseline result without creating an Origination or an Insights charge. A Monitor can instead use `baseline.risk_package_id`; the two baseline forms are mutually exclusive. Only choose a package your current key and product entitlement can access.

Supply related parties through top-level `participants`, or through `baseline.portfolio.application.participants` when the top-level list is omitted. If both are present, they must describe the same participants; a conflicting empty list does not silently discard submitted parties. Nonempty application `related_borrower_ids` must match those participants. Every admitted party needs continuous-monitoring authority and authorized evidence. See [related parties](/api-reference/related-person-verification).

## Recover and re-enroll the same facility

Retrieve the Monitor, resolve its `requirements` or `failure`, and obtain the latest ETag. Use `PATCH /v1/monitors/{id}` with `If-Match` and `{"status":"active"}` to resume `paused`, `requires_action`, `waiting_for_credits` or `failed`, or re-enroll `stopped`. Activation validates the active borrower, current product access, documents, policy and continuous-monitoring consent, then schedules evaluation durably. It does not invent a successful result or bypass missing prerequisites.

For changed sources, replace `connection_ids` with the full desired future source set. Reauthorize through the Hub first when consent is absent or revoked. Restore an archived borrower before resuming. Pausing or stopping fences pending publication; subsequent work cannot publish a package or charge against that suspended evaluation. Prior completed packages and charges remain unchanged.

## Find the same activity across resources

Use `GET /v1/monitors?institution_reference=...` with the facility's `deal.institution_reference`. Filter monitoring runs using `borrower_id` or `monitor_id`; each run returns its primary `borrower_id`. The corresponding events carry that borrower reference, so `GET /v1/events?borrower_id=...` can correlate product activity. Keep pagination filters unchanged while following a cursor.
