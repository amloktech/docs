Use `GET /v1/configuration` to discover the schemas, integration IDs, embedding versions and monitoring cadences approved for your key. The catalog of supported providers does not itself grant access to every integration or field.

## Lending-product catalog

`POST /v1/lending-product-versions` records one immutable lending-product revision. It captures borrower type, market, currency, amount and term bounds, repayment frequency, pricing and source documents. `pricing` must validate against the returned `pricing_schema_id`. Include the fees, rate and amortization inputs required for repayment analysis; AMLOK does not infer missing economics.

```json
{
  "external_id": "working-capital",
  "version": "1",
  "name": "Working capital loan",
  "borrower_type": "business",
  "market": "CA",
  "currency": "CAD",
  "product_type": "term_loan",
  "minimum_amount": {
    "amount": "10000.00",
    "currency": "CAD"
  },
  "maximum_amount": {
    "amount": "100000.00",
    "currency": "CAD"
  },
  "minimum_term_months": 6,
  "maximum_term_months": 24,
  "repayment_frequency": "monthly",
  "pricing_schema_id": "pricing_synthetic",
  "pricing": {
    "rate_type": "fixed",
    "annual_interest_rate": "0.12",
    "amortization_months": 12,
    "fees": []
  },
  "terms_document_ids": []
}
```

Read or list versions using the same resource. Create a new version when terms change; previous originations keep their original version and hash. Catalog products here are lending products, not merchant inventory.

## Risk policies

`POST /v1/risk-policy-versions` records approved typed rules and supporting policy documents. The rule language supports scalar comparisons (`gt`, `gte`, `lt`, `lte`, `eq`) against configured metric keys with matching units. Missing data routes to review. Policy documents provide context and are not automatically executable rules.

```json
{
  "external_id": "working-capital-policy",
  "version": "1",
  "name": "Illustrative policy, not a recommended threshold",
  "borrower_type": "business",
  "market": "CA",
  "rules": [
    {
      "id": "dscr-minimum",
      "dimension_key": "dscr",
      "operator": "gte",
      "threshold": "1.25",
      "unit": "ratio",
      "on_missing": "review",
      "on_fail": "review",
      "calculation_version": "amlok-dscr-1"
    }
  ],
  "policy_document_ids": []
}
```

The threshold above is synthetic and is not a recommended credit policy. Your institution supplies and approves its policy. Both rule definitions and evaluation results remain visible in the risk package.

## Application schemas

Every Origination supplies an `application_schema_id` and `declared_data`. Validate those fields against the matching JSON Schema from configuration. Compatibility checks also cover borrower type, market, currency, product and policy. Unsupported inputs produce a validation error rather than silently changing the assessment.

Owners manage organization/workspace settings and billing; Owners and Devs manage approved integration configuration. Versioned product and policy records are new records, never edits to prior assessment data.

## Runtime discovery

embedding_versions exposes each published Hub's allowed origins, return URLs, integrations and consent purposes. operational_profile supplies required limits and lifetimes. sandbox is null in Live; in Sandbox it exposes deterministic scenario IDs and the synthetic integration ID. Read the [operating profile guide](/api-reference/operating-profile) before implementing uploads, polling or recovery.
## Reuse product and policy versions across borrowers

A lending-product version describes your offering, not one borrower. Reuse its `id` as `lending_product_version_id` in multiple Origination requests or `baseline.portfolio` inputs. Reuse a compatible `risk_policy_version_id` in the same way. The borrower type, market, amount, currency and term must satisfy the referenced definitions.

For example, two Canadian business borrowers requesting CAD working capital can reference the same product version when both requests fit its limits. Their `borrower_id`, application, documents and authorized connections remain specific to each borrower. Use a different idempotency key for each intended origination.

Find a version using `GET /v1/lending-product-versions?external_id=working-capital&version=1`. Create a new version only when its definition changes. The sample pack deliberately creates separate named versions for its fictional businesses so each scenario can be inspected independently; that is not a requirement for your integration.
