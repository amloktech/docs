# AMLOK documentation product brief

## Audience and jobs

Financial-institution developers, risk teams, model validators, procurement teams, and authorized workspace administrators use this site to understand AMLOK, integrate its API, and assess the evidence behind its methods. Business and consumer underwriting require distinct validation populations.

## Product and terminology

AMLOK Insights performs a full underwriting. AMLOK Signal monitors changes and includes change-driven reassessment. Institutions make decisions and perform outreach in their own systems. Preserve the finalized API, pricing, credit, cancellation, and data-handling rules in AGENTS.md. Research does not change those contracts.

## Product API boundary

The November 2026 customer direction is a borrower-connection journey feeding Insights underwriting and Signal monitoring. Institutions supply application data, their lending-product catalog and risk policies. AMLOK returns an immutable risk package with financial dimensions and authorized underlying data and files. Collection, normalization, verification and orchestration belong behind that boundary. AMLOK has one public API with 67 operations under `/v1`, generated from `openapi/amlok.json`. The API reference, downloads, integration guidance and console Data Lookup must follow that same structure. The customer explicitly rejected parallel legacy APIs and migration references.

## Research evidence boundary

Research package 0.3 extends the acquired corpus and adds measured supervised SBA baselines. Package 0.2 builds an original-source inventory, Canadian financing cases, field semantics and real financial-document retrieval measurements. It specifies financial-language, event and graph training and matched frontier comparisons. It does not establish production foundation-model training, Canadian borrower validation or frontier superiority. Preserve actual source units, acquisition status and measured denominators. The prior 0.1 engineering experiment is retained only in local archival evidence, outside public pages and downloads. Do not relabel its outputs as observed data.

## Voice and presentation

Use concise, scientific language with explicit units, populations, task definitions, limitations, and primary-source citations. Use sentence case and regular dashes. Keep navigation icons on category containers. Use charts for measured quantities and diagrams for proposed architecture. Do not turn a research hypothesis into marketing copy or add invented results to make a comparison look complete.

## Review and publication

Prepare substantial research changes on a review branch. Preserve source records and private source assessments outside public documentation. Publish only within the user's authorization. Existing public product references remain separate from proposed research schemas.

## Institution completeness clarification

The November 6 follow-up confirms that Hub configuration belongs in the console, while borrower-bound launch sessions and connection visibility remain useful API capabilities. Institutions require all authorized collected and enriched data independently of completed assessments, complete application/document associations, and payment, wallet and consumption reconciliation. The contract adds nine read operations for these gaps; it does not expose enrichment jobs or add financial mutations.

## Backend build readiness

The user requested a complete implementation specification before building the backend. Define client-visible behavior, executable schemas, append-only lender updates, browser embedding, deterministic Sandbox scenarios and acceptance tests. Public documentation describes the complete API in present-tense customer language. Backend build status and runtime acceptance evidence remain in implementation/ and artifacts/, outside the documentation site. No new API version or exposed enrichment orchestration.

## Enterprise operating contract

The November 6 follow-up authorizes closing enterprise-volume documentation gaps. Preserve one API and its 67 operations. Define capacity discovery, bounded result representations, resumable complete exports, coordinated schema evolution and a unified data-model entry point. Keep environment-specific targets distinct from measured results and from the approved availability SLA. Runtime acceptance requires actual environment evidence recorded internally.

## Model correspondence

The Data Model distinguishes 63 source-normalized variants, the detailed verification aggregate, product responses and research-only representations. Source fields, state enums, catalog counts and schema pointers are generated and checked against the public contract; console Data Lookup imports the same field catalog. Capability associations for the full integration inventory do not change Active/In Review, Beta, markets or contractual entitlements. Research links explain correspondence without turning study labels, training manifests or measured population results into API fields or borrower-level findings.

## Sandbox developer experience

The November 7 direction adds six fictional business fixtures, 30 executable scenarios, a first-use empty/sample choice, and eight Sandbox-only controls. These extend the same API and do not add Live financial mutation commands. Prepare and test on staging; production release requires explicit approval.

The Documentation tab includes a customer-facing Sandbox section immediately after Pricing. Its setup screenshot uses a temporary example workspace. Explain the two starting choices, shared workspace scope, real API test records and simulated money clearly; do not describe test credits or scenario results as real funds, invoices or borrower decisions.

## Console user guides

The Console tab provides task-based onboarding and operations guides for workspace Owners, Developers and Analysts. It sits alongside Documentation, API Reference and Research, without duplicating the endpoint contracts. Screenshots come from the isolated demo deployment using synthetic businesses and payment records; never publish real borrower records, credentials, invitations or authenticator secrets. Demo is a separate deployment, not a third environment inside a customer's workspace.

Cover first-use sample/empty setup, organization/workspace/environment boundaries, read-only borrower review, connection and document evidence, draft Integrations Hub configuration, developer tools, workspace-specific invitations, security, and billing reconciliation. Ground controls and labels in the current console source and browser behavior. Distinguish completed processing from institution approval, events from delivery attempts, API traffic from billable consumption, and simulated funds from real payments. Do not invent Publish, retry, replay, funding or editing buttons that the interface does not expose. Preserve API-based execution instructions where the console is a reference or inspection view.

Organization Owners have broader access than workspace Dev/Analyst invitees. New invitations are workspace-specific; existing organization memberships retain their scope. Product records are read-only in the Console. Live access requires workspace activation. Public guides exclude the internal admin app and hosting or deployment administration.
