Use this prompt to build an AMLOK integration with your coding agent. It directs the agent to the current API specification and the workflows for your selected products.

## Choose your products

| Selection | Integration scope |
| --- | --- |
| Insights | Full underwriting from authorized evidence, with asynchronous results and completion-based consumption. |
| Signal | Portfolio monitoring from approved baselines, with alerts and included change-driven reassessment. |
| Insights and Signal | Full underwriting followed by monitoring, with shared business identifiers, evidence, and reporting. |

## Use the prompt

1. Open your application project in your coding agent.
2. Copy the prompt below and fill in **Application context** with your stack and selected products.
3. Keep API keys and signing secrets in your secret manager. Supply configuration names, not secret values.
4. Let the agent inspect your project and implement the selected flows.
5. Review the code and test results, then complete the documented sandbox checks before enabling production processing.

Your account manager provides client portal access and environment details. Authorized administrators create API keys in the portal. The [documentation MCP](/overview/mcp-server) and [agent skill](/overview/agent-skills) help your agent read the integration guidance.

[Open this page as Markdown](https://docs.amlok.io/overview/integration-prompt.md?version=1.0.0), or use the copy button to copy just the integration prompt:

```text AMLOK integration prompt
Build an AMLOK integration in this application using the current AMLOK
documentation and OpenAPI specification. Inspect the existing project first
and implement only the selected products and requested workflows.

APPLICATION CONTEXT
- Backend language and framework: [fill in]
- Selected products: [Insights, Signal, or both]
- Business use case and requested workflows: [fill in]
- Existing business/application identifiers: [describe the mapping]
- Existing authentication, storage, queue, and webhook receiver: [fill in]
- Environment: [sandbox by default]
- AMLOK environment origin: [provided by the account manager; no /v1 suffix]
- Credential storage: [secret-manager reference or environment variable names;
  never paste secret values]

READ FIRST
- https://docs.amlok.io/.well-known/skills/amlok-integration/SKILL.md
- https://docs.amlok.io/openapi/amlok.json
- https://docs.amlok.io/api-reference/products-and-endpoints
- https://docs.amlok.io/api-reference/authentication
- https://docs.amlok.io/api-reference/configuration
- https://docs.amlok.io/api-reference/sandbox-journeys
Use https://docs.amlok.io/llms.txt to discover additional pages. If the AMLOK
documentation MCP is connected, use it to search and read the relevant guides.
Read endpoint schemas before constructing requests. Do not invent endpoints,
SDK packages, environment URLs, provider capabilities, or successful results.

ACCESS AND SETUP
1. The account manager provides client portal access and environment details.
   Authorized administrators create API keys in the portal. Do not implement
   programmatic signup, API-key creation, or a new portal workflow.
2. Set AMLOK_API_BASE_URL=https://api.amlok.io (without /v1) and read
   AMLOK_API_KEY server-side. Sandbox and Live use the same origin; the key
   selects the workspace environment. Never expose the key
   in the browser, prompts, logs, source control, or exported examples. Store
   webhook signing secrets separately. Use HTTPS and reject unexpected redirects.
3. One API key identifies one workspace, institution, and environment. Derive
   authorized subject access from the application's authenticated user. Do not
   let caller-supplied workspace IDs change the key's scope.
4. Read environment configuration and provider capabilities. Use returned IDs,
   approved application and pricing schemas, entitlements, consent scopes, and runtime limits.
   Use borrower-bound embedding sessions to obtain authorization before connecting
   production data. Use only provisioned synthetic fixtures in sandbox tests.

PRODUCT FLOWS
- Insights: create a borrower and short-lived embedding session. AMLOK captures
  consent and handles provider authorization and source collection. Submit an
  Origination with the application, exact lending-product and risk-policy
  versions, connections and documents. Follow its status and requirements, then
  retrieve the risk package and frozen evidence. Do not orchestrate workflow,
  verification, sync, calculation, manifest or processing-context endpoints.
- Signal: enroll a funded deal with an existing risk package or approved portfolio
  onboarding reference. AMLOK handles baselines and collection. Follow monitoring
  runs, package changes and alerts; use events and delivery attempts for reliable
  notification. Change-driven reassessment is included in Signal. The monthly
  borrower/business/workspace charge is not multiplied by several monitors.
- Reporting: use billing summary, immutable transactions and typed exports for
  usage, credits, statements, funding, rates and workload. Distinguish available
  credits from cumulative spent credits. Do not introduce held/reserved buckets.
- Only Insights and Signal are paid products. KYB/KYC and other checks are included
  internal stages. Related people are application.related_borrower_ids; the parent
  business remains the product billing subject.

RELIABILITY AND DATA
- Persist one idempotency key, operation ID, target path, and intended body for
  each intended command. Reuse them for retries of that action. After the
  24-hour full-response replay window, recover accepted work through its durable
  receipt; never create a new paid request solely because a response was lost.
  Follow https://docs.amlok.io/api-reference/request-recovery.
- Handle pagination, asynchronous jobs, rate limits, insufficient credits,
  partial data coverage, and source authorization expiry using the actual
  documented states. Discover limits from configuration rather than examples.
- Verify X-AMLOK-Signature over the exact raw body before parsing. Use the
  destination's signing secret, the documented five-minute timestamp tolerance,
  constant-time comparison, and durable event-ID deduplication. Check workspace
  association, handle resource versions and out-of-order delivery, and persist
  the event before acknowledging. Read the current webhook guide and helpers.
- Preserve immutable evidence and source coverage. Missing data is unavailable,
  not zero. Use snapshot-bound collection bootstrap and durable event-feed cursors when
  synchronizing local data. Never treat a requested cadence as source freshness.
- Insights includes at least 12 months of banking history within the agreed
  record limit. Signal counts new processed record versions in the month; do not
  recount unchanged baseline history or retries of an unchanged version. Use the
  Amlok-assessed analysis complexity, independently of record volume, and enforce operational capacity separately.
- Keep monetary values exact. Where billing calculations are needed, round the
  effective unit rate to two decimals with decimal half-up rounding, then round
  each quantity-times-rate line; sum the rounded lines.

BOUNDARIES
- Financial APIs provide reporting and exports. Do not create wallet, top-up,
  payment-method, transfer, withdrawal, payout, refund-request, cancellation, or
  deletion commands. Payment settings and cancellation belong in the portal;
  enterprise clients may also cancel through their account manager.
- Respect cancellation and authorization states. Do not resume or replace work
  after cancellation; processing, deductions, and upcoming top-ups stop then.
- AMLOK provides risk assessments and intervention signals. Do not add servicing
  cases, borrower messages, collections, or credit-decision execution. Institution
  staff handle intervention in their own systems.
- Skills and the documentation MCP do not grant permission to execute API calls.
  Do not send production requests or start chargeable processing without explicit
  authorization for that action. Keep customer data out of documentation queries.

DELIVERABLES AND CHECKS
Implement the selected backend routes, client calls, state persistence, webhook
receiver, and tests using the project's existing patterns. Include a setup guide
and a configuration example containing names or placeholders, never secrets.

Test valid and invalid signatures, stale timestamps, duplicate and out-of-order
events, timeout recovery, insufficient credits, missing evidence, expired source
authorization, and workload-limit errors. For selected products, verify one
Insights completion charge and one Signal charge per business/month, including
multiple monitors and change-driven reassessment without another Insights charge.

Run the documented sandbox journeys only when the user provides an authorized
sandbox and its fixtures. Report changed files, tests actually run, any live run
IDs, unresolved prerequisites, and production-enablement steps. Distinguish local
or mocked validation from a completed live sandbox journey.
```

## Review the result

Ask your agent to show the implementation, actual test results, and remaining setup steps. A local or mocked test does not prove that a request completed in your sandbox.

Confirm that the integration uses your approved integrations, products and policies, preserves workspace isolation, and handles duplicate requests and events without duplicate effects. For Signal, confirm that multiple monitors and change-driven reassessment do not create additional monthly product charges.
